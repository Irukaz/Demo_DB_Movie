# DDL and the deployed Cinema67 demo

The PostgreSQL production DDL uses schema cinema67 and 15 business tables from the report. Each write updates the relational tables and public.demo_state in one transaction. Existing plural tables from the earlier demo are retained as legacy data and are no longer written by this version.

The original report script is preserved as cinema67_report_oracle.sql. cinema67_report_postgresql.sql is a literal PostgreSQL conversion for study. cinema67_production_postgresql.sql is the business DDL deployed by the app.

Production adjustments: TICKET_STATUS and an active-ticket partial unique index preserve cancelled/changed tickets while allowing seats to be booked again. PROMOTION adds DISCOUNT_KIND and MINIMUM_AMOUNT to support the existing percentage/fixed discounts. All 15 original table names and their primary/foreign keys remain.

The demo also retains an implementation snapshot (public.demo_state) for branch labels, posters, products, request forms and UI revision control; these details are not fields in the report DDL. The database inspector reads real SQL rows, counts and columns, rather than displaying the snapshot.

Existing customers without names receive Guest / Demo placeholders. New checkouts collect first/last names. Demo employee IDs 1-5 represent management, finance, call center, HR and front desk. No authentication is added.

TICKET retains history and SHOWTIME_SEAT reflects active holds and paid bookings. PAYMENT history is retained after a subsequent cancellation. BOOKING_OPERATION and COMPLAINT_OPERATION are generated by the server, not trusted from client input.

On first startup, existing booking IDs, contacts, totals, statuses and requests are migrated without resetting the demo. Relational identifiers are deterministic numeric mappings of existing UI codes. RELEASE_DATE is NULL because this demo does not collect release dates.

This remains a presentation demo. Relational rows are regenerated within a transaction on each write; the snapshot and business rows are kept consistent, but this approach is not designed for a large production workload.
